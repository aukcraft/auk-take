# ADR 四问模板与示例

## 模板

```markdown
## ADR-NNN <一句话决策标题>

**决策**：<将做什么 / 禁止什么，可验证的陈述>
**动机**：<什么问题迫使这个决策；不做会怎样>
**代价**：<牺牲了什么、增加了什么复杂度——必须诚实写；没有代价的决策是空话>
**验证**：<用什么客观手段保证决策被遵守：测试、lint、CI 检查、目录约定>
```

四问缺一不可：
- 无决策 → 讨论记录，不是 ADR
- 无动机 → 后来者会"优化"掉它
- 无代价 → 不可信（一切决策都有代价）
- 无验证 → 只是愿望；验证方式让它变成可执行约束

## 示例（摘自真实实践）

```markdown
## ADR-001 核心模块零平台依赖
决策：core 禁止 import react-native / @tauri-apps / DOM / Node 专属 API。
动机：业务逻辑不感知宿主环境，才能在纯 Node 测试并复用到任意壳。
代价：HTTP/时钟/哈希/持久化必须抽象为 Port / SettingsStore 接口，多一层间接。
验证：core 测试在纯 Node + vitest 下运行，无任何 UI 框架（CI 里跑 = 持续验证）。

## ADR-005 source id 由内容哈希派生
决策：实例 id = kind:<hash(用户配置)>。
动机：同一配置重复添加天然去重；多实例共存不冲突（曾因固定 id 导致覆盖，已修复）。
代价：配置归一化逻辑要稳定（URL 尾斜杠等差异会派生不同 id）。
验证：去重回归测试——同配置 connect 两次断言同一 id。
```

## 维护规则

- 编号只增不改；推翻旧决策写新 ADR 并标注"supersedes ADR-NNN"
- ADR 放核心包旁（docs/adr.md），改核心前先读
- 每个 ADR 的"验证"栏应可直接翻译成 CI 步骤或测试用例
